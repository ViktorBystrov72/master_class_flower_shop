# Layero

Layero — хостинг и публикация сайтов со сборкой и раздачей в России. Проект
либо подключён к репозиторию, либо загружается из папки. Платформа собирает
его и отдаёт на `<проект>.layero.app`. Есть свои домены, превью веток,
runtime-приложения, переменные окружения, аналитика и Postgres с Data API.
Панель — `https://app.layero.ru`, документация — `https://docs.layero.ru`.

## Ответ в чат

После успешной публикации сообщение человеку **обязано** содержать живую
ссылку на сайт. Бери её как есть из `ready.url` (CLI) или из URL в ответе
`publish_site` / `site_status` (MCP). Для push в прод тоже верни адрес сайта,
а не только коммит. Не заканчивай ответ одной панелью, номером сборки или
словом «готово». Если запуск не удался, так и напиши и не подставляй
выдуманный адрес `.layero.app`.

## Три пути — выбери по ситуации

| Ситуация | Путь |
|---|---|
| (a) Есть репозиторий на GitHub, GitVerse, GitLab, GitFlic или SourceCraft | Подключи: `npx layero@latest projects create --repo <provider>:<owner/repo> --json` (провайдер с токеном — `npx layero@latest sources connect <provider> --token-stdin`; GitHub — установка App в панели) или в панели **Создать проект → Импорт из репозитория**. Дальше push в ветку = превью, push в `main` = прод. Подробности — [references/git-providers.md](references/git-providers.md). |
| (b) Есть папка с кодом, репозитория нет или он не нужен | `npx layero@latest deploy --json` — CLI упакует папку, платформа соберёт. Готовую статику можно опубликовать через MCP `publish_site`. |
| (c) Сайт уже на Layero | Диагностика (`diagnose_deploy` в MCP / `npx layero@latest diagnose`), логи, откат, окружения (`envs list`), домены, переменные, аналитика, Data API — через MCP или CLI. |

Как отличить: человек работает с репозиторием — (a); просит «выложи вот эту
папку» — (b); спрашивает про уже живой сайт — (c). Не превращай (b) в (a):
для деплоя `git init` не нужен.

## CLI

```bash
npx layero@latest deploy --dry-run --json   # план сборки; ничего не заливает, вход не нужен
npx layero@latest deploy --json
```

`--json` включает JSON-строки: один объект на строку stdout. Смотри поле
`event`, не разбирай человекочитаемый текст. Внутри агента и при stdout без
TTY режим включается сам.

`--dry-run` показывает, как платформа соберёт папку: фреймворк, команду
сборки, папку результата, откуда взялось каждое значение (`layero.json`,
настройки проекта, `package.json`, значение фреймворка по умолчанию) и
заменит ли выкладка живой сайт. Если `confident` равен `false`, до первого
деплоя сделай то, что сказано в `next_action` (подробности в разделе
`layero.json`). `npx layero@latest init` необязателен: он дописывает блок
правил в `AGENTS.md`, настройки не записывает, а `deploy` сам привязывает
папку.

С токеном деплой — одна неинтерактивная команда:
`LAYERO_TOKEN=… npx layero@latest deploy --name <имя> --yes --json`.
Нет аккаунта, нет токена или человека нет у клавиатуры:
`npx layero@latest deploy --claim --yes --json` — без входа (ниже, «Аккаунта
Layero нет»).

Главные события:

- `auth_required` — `url` и `user_code`. Покажи `url` кликабельной ссылкой.
  CLI ждёт вход сам (опрос каждые 2 с, токен кэшируется в
  `~/.layero/config.json`). Локального callback нет — браузер может быть на
  другой машине; работает из SSH, Docker и песочницы.
- `detected` — как CLI видит папку: фреймворк, команда сборки, папка
  результата, `sources`, `confident`. Это совет: платформа решает по
  загруженным файлам, и догадка в проект не сохраняется. При `confident:
  false` есть `hint` и `next_action` — выполни их.
- `build_log` — сырой лог; в чат пересылай только строки с ошибками.
- `ready` — `url` это живой адрес сайта, он уже отвечает: CLI ждёт (до 90 с),
  пока адрес отдаёт сайт, а не страницу платформы. В ответ в чат **вставь
  этот `url` кликабельной ссылкой, как есть**. Не собирай хост по шаблону и
  не заканчивай ответ только `dashboard_url`, id деплоя или «готово»:
  `dashboard_url` — панель, не сайт. `edge_ready: false` значит, что
  приложение не поднялось — так и скажи, ссылку не выдумывай; читай
  `npx layero@latest logs --runtime`.
- `error` — стабильные `code` и `next_action`. Выполни `next_action` (для
  упавшей сборки это `npx layero@latest diagnose --deploy <id>`, работает и
  без аккаунта).

Повторный деплой — та же команда: первый запуск создаёт проект, следующие
его переиспользуют; коммит между запусками не нужен. Полный список событий,
полей, кодов ошибок и кодов выхода —
[references/json-events.md](references/json-events.md). Каждая команда в
`--json` печатает события; код выхода задаёт класс: 2 — нужен вход, 3 — не
найдено, 4 — неверный ввод, 5 — ошибка на стороне платформы.

**Аккаунта Layero нет** — `npx layero@latest deploy --claim --json`:
платформа создаёт временный сайт на 1 час, и CLI печатает событие
`claimable` с `claim_url` **до** `ready`. Только статика и SPA: серверное
приложение (SSR, fullstack, контейнер) отклоняется кодом `claim_static_only`
ещё до загрузки — ему нужен аккаунт. Адрес случайный и закрыт от поисковиков.
Отдай человеку `ready.url` и `claim_url`: забрать сайт в аккаунт может только
он, в панели. Режим включается ТОЛЬКО с `--claim`: без него и без токена
`deploy` просит вход (`auth_required`) — покажи человеку `url` и `user_code`
и жди. Публикация без аккаунта — решение человека, не твоё: `--claim` только
если он попросил или согласился. Песочница создаёт только новый проект:
`--claim` вместе с `--project` даёт ошибку `claim_with_project`. Перенос
сайта в аккаунт стирает переменные окружения, хуки деплоя и настройки
сборки, заданные без аккаунта.

### CI

Вход через браузер на раннере невозможен — нужен токен:
`npx layero@latest token create` или `https://app.layero.ru/settings/cli`.

```bash
LAYERO_TOKEN=… npx layero@latest deploy --project <slug> --json --yes
```

`LAYERO_TOKEN` перекрывает сохранённый локальный вход. `--yes` пропускает
подтверждение, которое иначе ждало бы вечно. `--project`, не `--name`:
`--name` только называет проект при создании, и пайплайн из чистого
checkout без `.layero/project.json` создавал бы новый проект на каждом
запуске.

## MCP

Сервер `https://mcp.layero.ru/mcp` (Streamable HTTP), имя в конфиге клиента
— `layero`. Подключение: `npx -y add-mcp https://mcp.layero.ru/mcp` или
плагин Claude Code / Cursor из `LayeroInfra/layero-agents`. Без входа
доступны `search_docs`, `check_copy`, `refactor_site`; остальное требует
OAuth (клиент откроет браузер при первом вызове инструмента аккаунта) или
заголовка `Authorization: Bearer $LAYERO_TOKEN` для CI.

Группы инструментов:

- **аккаунт и проекты** — `whoami`, `my_projects`, `list_sources`
  (провайдеры и подключения), `import_repo` (проект из репозитория — путь
  (a) без панели; сам заканчивает мастер настройки и запускает первую
  сборку, не закрепляя угаданные фреймворк, команду сборки и папку
  результата — сборщик определяет их по репозиторию на каждой сборке; поле
  `setup`: `applied` / `pending` / `failed`; `deploy=false` оставляет проект
  в мастере; токен провайдера подключает человек в панели, не агент),
  `project_create` (пустой проект для последующего `publish_site`),
  `list_environments` (ветки с адресами и последними сборками),
  `project_settings` (прочитать или сменить папку приложения, команды, папку
  результата и тип проекта — выход, когда детект ошибся; приложение в
  подпапке монорепо импортируется через `import_repo(root_directory=…)`);
- **сайт** — `site_status` (`wait_s` ждёт идущую сборку, `path` проверяет
  маршрут API-сервера), `env_vars`, `read_site`, `site_screenshot`,
  `site_issues`, `refactor_site`, `check_copy`, `check_performance`,
  `check_rules` (правила против фишинга, см. ниже);
- **деплои** — `list_deploys`, `deploy_logs`, `diagnose_deploy`
  (`build_facts`: чем сборка реально пользовалась), `retry_deploy`
  (`redeploy=true` пересобирает последний коммит без push),
  `cancel_deploy`, `rollback`, `publish_site`
  (старое имя `publish_landing` — устаревший псевдоним);
- **домены и аналитика** — `connect_domain`, `check_domain`,
  `list_domains`, `connect_analytics`, `site_analytics`;
- **Data API** — `data_api_status`, `data_api_methods`, `data_api_grant`,
  `data_api_keys`, `data_api_origins`, `data_api_probe`.

Нужно явное согласие человека: `rollback` (меняет то, что видят посетители),
`data_api_grant` (открывает доступ к данным), `data_api_keys` с
`issue`/`revoke`, `data_api_origins`. Клиент с формами получает вопрос от
сервера; без форм — спроси в чате и только потом передай `confirmed`. Никогда
не подставляй `confirmed` вместо ответа человека.

## `layero.json`

**Файл — ответ на одну конкретную проблему: один симптом, одно поле. Это
никогда не анкета.** Сначала посмотри на папку: обычное одно приложение
деплоится вообще без файла; формы ниже настраиваются до первого деплоя.
Каждое записанное поле перестаёт определяться автоматически и закрепляется
в панели, а неизвестный ключ молча пропускается — не пиши файл «на всякий
случай».

**Перед созданием или правкой `layero.json` обязательно прочитай
[references/layero-json.md](references/layero-json.md)** — полный список
ключей, таблицу «симптом → поле» и строки лога, которые доказывают, что
значение применилось. Не пиши файл по памяти.

Когда сборка или запуск падают:

1. Возьми настоящую ошибку из лога (`diagnose_deploy` → `deploy_logs`, или
   `npx layero@latest diagnose` / `logs`) — не действуй по тексту карточки.
2. Смотри упавшую стадию: `detect` — форма приложения (корень, тип,
   `runtime`), не код; `install` — lockfile; `build` — процитированная
   строка ошибки; `verify` / `upload` — `outputDirectory`; `launch` —
   `startCommand`, `port`, переменные.
3. Найди симптом в таблице справочника и измени ровно одну вещь.
4. Проверь в логе сборки, что значение применилось (`(from layero.json)`) и
   что файл не дал предупреждений.
5. Та же ошибка два раза подряд — остановись и скажи человеку; третьего
   деплоя не будет.

До первого деплоя запусти `npx layero@latest deploy --dry-run --json`. Если
папка не распознана (`confident: false`), форма названа в `hint`, а
исправление — в `next_action`: приложение в подпапке → `--root <каталог>`;
приложение workspace, которое импортирует соседний пакет → `layero.json` в
корне workspace с `"framework": "generic"` + `buildCommand` +
`outputDirectory`; свой скрипт сборки без известного фреймворка →
`"framework": "generic"` (`static` сборку никогда не запускает); сервер →
`-t node_web` / `-t python_web`; `frontend/` + `backend/` → блоки
fullstack. Формы и файлы — в справочнике.

`--dry-run` не читает код. Для любого сервера сначала открой точку входа:
она должна слушать `0.0.0.0` (не `127.0.0.1`) и `$PORT`, а команда запуска
должна выполнять файл, который существует после сборки (`node dist/index.js`,
не исходник `.ts`) — текст ошибки запуска эти причины не называет.

Файлом не лечится: корень монорепо → `--root`; деплой не из той папки →
`cd` или `--root`; режим Next.js сервер/экспорт → `next.config`; ошибки
кода → код; секреты и переменные → переменные проекта (`env set`); сбои
платформы → одна повторная попытка.

В файле нет секретов, токенов, доменов и id — он лежит в git.

## Провайдеры Git

GitHub, GitVerse, GitLab, GitFlic, SourceCraft — все подключаются в панели
через «Импорт из репозитория». Push в ветку — превью-окружение, push в
`main` — прод. Различия —
[references/git-providers.md](references/git-providers.md).

## Правила содержания

Каждый сайт на Layero следует правилам против фишинга
(`https://layero.ru/rules`): не собирать учётные данные чужих сервисов, не
показывать фальшивые предупреждения, не заманивать в мошенничество, не
выдавать себя за чужой бренд, не делать скрытых редиректов, не раздавать
вредоносное ПО. После деплоя `publish_site` и `site_status` добавляют
`rules_warnings` только когда сайт совпал с правилом — тогда сначала скажи
человеку и не помогай обойти проверку; нет поля — нечего говорить. Чеклист
и то, что делает платформа при совпадении, — навык `layero-content-rules`.

## Никогда

- Не заканчивай успешную публикацию без ссылки на сайт в ответе в чат.
- Не делай `git init` и не пушь в репозиторий ради деплоя — единица деплоя
  CLI это папка.
- Не ставь `npm install -g layero` — глобальная установка в песочнице агента
  часто падает. Только `npx layero@latest …` или `npm install -D layero`.
- Не открывай панель, чтобы «доделать настройку»: CLI делает всё сам,
  браузерного мастера нет с v0.5.0.
- Не вызывай `layero login --provider` — флага нет с v0.5.x; провайдер
  выбирается в браузере.
- Не считай `layero deploy` безопасным превью: у CLI-проекта прямая
  загрузка сама выкатывается в прод и заменяет то, что посетители видят на
  `ready.url`. `--prod` имеет смысл только у проекта с подключённым
  репозиторием.
- Не предлагай `--branch` как изолированную публикацию: `deploy` отклоняет
  флаг кодом `branch_unsupported` — прямые загрузки попадают в окружение
  `cli`. Изолированное превью — только push в ветку подключённого
  репозитория (`projects create --repo`).
- Не принимай claim и не удаляй проект за человека: `claim accept` только
  открывает ссылку, `projects delete` требует область `admin` и явный
  `--yes` от человека.
- Не собирай адрес сайта по шаблону — только `ready.url`.
- Не публикуй в прод молча и не откатывай без вопроса.
- Не выдумывай ключи `layero.json` — существуют только имена из справочника.
- Не заполняй `layero.json` как анкету — один симптом, одно поле.
- Не делай третий деплой после двух одинаковых ошибок;
  `--confirm-repeated-failure` — для человека, не для тебя.
- Не правь код при ошибке на стадии `detect` — чинится форма приложения
  (корень, тип, `runtime`), не код.
