# `layero.json` — сборка и runtime в репозитории

Читай это перед тем, как создать или править `layero.json`, и всякий раз,
когда сборка или запуск на Layero падают. Текст собран по боевым данным:
1269 упавших сборок за 90 дней, что их вызвало и какие из них этот файл
может и не может починить.

## Одно правило

**`layero.json` — ответ на одну конкретную проблему: один симптом, одно
поле. Это никогда не анкета.**

Решай в таком порядке:

1. **Сначала посмотри план:** `npx layero@latest deploy --dry-run --json`
   (ничего не заливает, вход не нужен). Если `confident` равен `false`,
   папка — одна из форм, которые детект не может закрыть сам: приложение в
   подпапке, приложение workspace с соседним пакетом, свой скрипт сборки без
   фреймворка, сервер, `frontend/` + `backend/` — и `hint` / `next_action`
   называют форму и исправление (таблица «Когда папка не распознана»).
   Настрой эту форму **до** первого деплоя. Деплой, который точно упадёт, —
   не проба, а потраченная сборка.
2. **Иначе деплой без файла.** Обычному одному приложению (Vite, Next,
   Astro, CRA, SvelteKit, Nuxt, простой HTML…) ничего не нужно.
3. **После сбоя** добавь ровно то поле, которое называет таблица симптомов.

- 84 % новых проектов выходят в прод с первой сборки вообще без файла.
  Детект уже находит фреймворк, менеджер пакетов, скрипт сборки, папку
  результата, версию Node, команду запуска и порт.
- Каждое записанное поле **перестаёт определяться автоматически и
  закрепляется в панели**. Значение, скопированное «на всякий случай»,
  становится ложью в день, когда проект сменит сборщик.
- Около 60 % сбоев файлом не лечатся вообще: их чинят в другом месте (см.
  «Чего файл НЕ чинит»). Агенты, которые продолжали править код или файл
  для проблемы вне обоих, давали серии до 61 одинакового сбоя подряд.

## Порядок, когда сборка или запуск падают

1. **Читай настоящую ошибку, не карточку.** 13 % сбоев показывают только
   `docker-build: exit code 1` или `command failed: npm run build`. Сначала
   возьми лог: MCP `diagnose_deploy`, затем `deploy_logs`, или
   `npx layero@latest diagnose` / `npx layero@latest logs` (добавь
   `--runtime` для вывода работающего приложения). Никогда не правь файл
   только по тексту карточки.
2. **Смотри стадию, которая упала** — она говорит, где живёт исправление:

   | Стадия | Где исправление |
   |---|---|
   | `detect` | *Форма* приложения: корневая папка, тип проекта, `runtime`. Не код. |
   | `install` | Lockfile и `packageManager` в репозитории; затем `installCommand`. |
   | `build` | Процитированная строка ошибки: обычно код, иногда `buildCommand` / `nodeVersion`. |
   | `verify`, `upload` | `outputDirectory`. |
   | `launch` | `startCommand`, `port`, переменные окружения. |
   | `clone`, `timeout`, `activate` | Платформа или доступ к источнику. Повтори один раз. |

3. **Найди симптом в таблице ниже и измени ровно одну вещь.**
4. **Проверь в логе сборки** (раздел «Как проверить»), что значение
   применилось и файл не дал предупреждений.
5. **Та же ошибка два раза подряд — остановись.** Третий раз не деплой.
   Перечитай лог и эту таблицу; если класс «файлом не чинится», так и скажи
   человеку и назови действие, которое чинит. После десяти одинаковых
   сбоев подряд платформа ставит на паузу автодеплои из git, а CLI требует
   `--confirm-repeated-failure`; этот флаг для человека, не для тебя.

## Симптом → исправление

Строки в кавычках — то, что буквально будет в карточке деплоя, событии CLI
или логе сборки. Их не перефразируй при поиске.

### Чинится через `layero.json`

| Симптом | Исправление |
|---|---|
| `собранный сайт не содержит index.html в '.'` · `похоже, раздаётся исходный код репозитория, а не собранный сайт` · `сборка отработала, но папки 'dist' нет. После сборки в каталоге есть: …` · `[output] в 'dist' нет index.html` | `outputDirectory`: папка, в которой после сборки лежит `index.html` (`dist`, `dist/client`, `dist/<app>/browser`, `.output/public`, `build/client`). Ошибка перечисляет, что есть на диске — путь бери оттуда. Если проект определён как «Static (no build)», но сборка нужна, задай ещё `framework` и `buildCommand`. |
| `Сборка НЕ запускалась: проект собирается как статический сайт (фреймворк «static») …` · в логе `[config] ВНИМАНИЕ: buildCommand из layero.json (…) НЕ выполняется` или `static framework: skipping install/build` | **Сборка вообще не запускалась.** `framework: "static"` (из файла, настроек проекта или потому что в папке html и нет известного фреймворка) значит *нет установки и нет сборки*; `buildCommand` при этом не выполняется — ошибка называет команду, которая не запустилась. Для проекта со своим скриптом сборки и без известного фреймворка используй `"framework": "generic"` вместе с `buildCommand` и `outputDirectory`. Не начинай менять путь результата — путь никогда не был проблемой. Здесь `diagnose` отвечает `next_actions: ["fix_config"]`: повтор упадёт так же. |
| `npm error Missing script: "build"` · `в package.json нет скрипта «build», а сборка настроена как …. Доступные скрипты: dev, test` · `не знаем, чем собирать этот проект: команда сборки не задана` | `buildCommand` со скриптом, который существует. Если сайту сборка не нужна вовсе: `"framework": "static"`. Если это сервер или бот, это не статический сайт — см. следующую строку. |
| Сервер Node или Python опубликован как статический сайт (отдаются файлы, ничего не работает), или лог говорит `в приложении больше нет серверной части — дальше оно раздаётся файлами, а не работает в контейнере` про репозиторий, который **является** сервером | Платформа сама переключается между статикой и контейнером, когда узнаёт сервер (Next без `output: 'export'`, Express, Fastify, FastAPI, Flask, Django…). Когда не узнаёт, объяви: `"runtime": "node_web"` (или `"python_web"`, `"ssr_next"`), `"startCommand": "node dist/server.js"` и `"port"`, если он не по умолчанию. `runtime` верхнего уровня побеждает тип проекта; лог говорит `the file wins`. Разовый вариант без файла: `npx layero@latest deploy -t node_web`. Если приложение на самом деле статическое, тип неверный: задеплой снова с `-t vite` / `-t static`. |
| `launch/boot: container failed to start in time` с `ERR_MODULE_NOT_FOUND /app/…`, отсутствующим файлом входа или приложением, слушающим `127.0.0.1` | `startCommand`: путь относительно `/app`, файл, который существует **после** сборки, слушает `0.0.0.0` и `$PORT` — например `uvicorn main:app --host 0.0.0.0 --port $PORT`. Задай `port`, если приложение слушает иначе (по умолчанию: Node 3000, Next 8080, Python 8000, Streamlit 8501, Gradio 7860). ASGI-приложению нужен `uvicorn`, не `gunicorn app:app`. |
| `ERR_UNKNOWN_BUILTIN_MODULE` · `EBADENGINE` · `Node.js v… ERR_INVALID_PACKAGE_CONFIG` · `Node.js 18 снят с поддержки и закрыт для новых сборок` | `"nodeVersion": "22"`. Сначала посмотри строку лога `[config] node=… (…)`: если `.nvmrc` или `engines.node` уже задают версию, исправь там — файл перекроет их и оставит два источника правды. |
| `npm error code EUSAGE` (lock не синхронен) · обрезанный вывод `npm help ci` (нет lockfile) · `ERR_PNPM_…` | Сначала репозиторий: закоммить актуальный lockfile и точный `packageManager`. Только потом `installCommand` (`npm install`, `pnpm install --no-frozen-lockfile`). Никогда не пиши `npm ci` как *свой* `installCommand`, когда lockfile нет. (Без `installCommand` платформа справляется сама: запускает `npm ci` и откатывается на `npm install`; одного отсутствия lockfile недостаточно, чтобы добавлять ключ.) |
| `/bin/sh: 1: run: not found` · `-v: not found` | Команда — обрывок. Пиши команду целиком: `npm run build`, не `run build`. |
| `Can't resolve '@scope/shared'` в workspace | Деплой из **корня workspace** (не `--root apps/web`: соседний пакет не загрузится) со всеми тремя ключами — `"framework": "generic"`, `buildCommand`, который сначала собирает зависимости (`pnpm --filter @scope/shared build && pnpm --filter @scope/web build`), и `outputDirectory: "apps/web/dist"`. Без `framework` корень workspace угадывается как `static`, и сборка не запускается. Полный пример: «Минимальные примеры». `Unsupported URL Type "workspace:"` значит, что lockfile менеджера workspace не загружен — закоммить его. |
| Фронтенд и бэкенд в одном репозитории выкладываются только как статический сайт | Блоки fullstack: `frontend` + `backend` (+ `apiPrefix`). См. «Раскладка fullstack». |

### Чего файл НЕ чинит

| Симптом | Что чинит |
|---|---|
| `no app at the repo root, and multiple candidate app folders found (…)` · `root_directory not found in source: 'apps/web'` · `no package.json at the build root` | **Корень приложения — настройка проекта, не ключ файла.** `npx layero@latest deploy --root apps/web` (сохраняется на проекте) или «Корневой каталог» в панели. Ключа `rootDirectory` нет. В монорепо `layero.json` живёт **внутри папки приложения**, не в корне репозитория. Исключение: половины fullstack используют `frontend.root` / `backend.root`. |
| `branch 'cli' has no app to build: no package.json / layero.json / requirements.txt found at the deploy root` | `deploy` запущен не из той папки. `cd` в приложение или передай `--root`. Готовая статика: `--prebuilt <каталог>`. |
| Next.js: `"/app/.next/standalone": not found` · `Next собрал статический сайт… Запустите сборку ещё раз` · `project is configured for SSR, can't deploy as static` | **`next.config`, не файл.** `output: 'export'` значит статика, отсутствие `output` значит сервер. Никогда не ставь `outputDirectory: ".next"`. «Запустите сборку ещё раз» буквально: повтори один раз. Если это вообще не Next (Vite SSR, TanStack Start), тип неверный — `"runtime": "node_web"` + `startCommand`. |
| `error TS…` · `Type error:` · `Module not found: Can't resolve '@/…'` · `Failed to compile` · падающие тесты внутри `build` | Код. Воспроизведи локально той же командой и той же мажорной версией Node. Частый случай: регистр имени файла, который macOS прощает, а Linux нет. Выкинуть шаг сборки (`vite build` вместо `tsc -b && vite build`) можно только если владелец согласен. |
| `launch/probe: container bound but not servable (5xx)` · `launch/probe: container bound but not servable (no HTTP response)` | Окружение, база, код: `GET /` должен отвечать без 5xx. Переменные идут в панель или `npx layero@latest env set`, не в файл. Бот с длинным опросом без HTTP-слушателя проверку запуска не пройдёт. |
| `supabaseUrl is required` · Prisma `timed out` во время сборки · `Failed to collect page data` | Переменные окружения проекта на время сборки. Секреты в файл не кладутся. |
| `builder did not pick up the job after N retries` · `deb.debian.org` · `auth.docker.io … TLS handshake` · `container has no IP in apps network` | Платформа. Повтори **один** раз (`retry_deploy`). Если повторяется, скажи человеку написать в поддержку — код и файл не трогай. |
| `docker-build: timeout after …s` · `Reached heap limit` · `ENOSPC` | Лимиты сборки тарифа. `memory_mb` в файле — память *работающего контейнера*, не сборки. |
| `хост '…' не в списке разрешённых источников` · `git-fetch: timeout after …s` | Подключение источника в панели. |

## Когда папка не распознана

`npx layero@latest deploy --dry-run --json` (и событие `detected` каждого
деплоя) показывает, как платформа соберёт папку, с источником каждого
значения в `sources`: `layero.json`, `project settings`, `package.json`,
`framework config`, `framework default`. Это совет, не решение: платформа
определяет снова по загруженным файлам, и CLI никогда не сохраняет догадку
в проект — только то, что ты называешь (`--type`, `--root`, `layero.json`,
поля, которые ты сам пишешь в `.layero/project.json`).

`confident: false` значит, что папка не распознана. Тогда в событии есть
`hint` (что увидел CLI), `next_action` (один конкретный шаг) и `candidates`
(папки приложений ниже). Формы и куда указывает `next_action`:

| Что в папке | Что делать |
|---|---|
| Приложение в подпапке (`apps/web`, `frontend/`, `packages/site`) и оно **самодостаточно** (нет зависимостей `workspace:*` / `file:../`) | `npx layero@latest deploy --root apps/web` — это не ключ файла, см. ниже. При одной папке приложения платформа выбирает её и сама; `--root` делает выбор явным |
| Приложение в подпапке и **зависит от соседнего пакета** workspace (`"@scope/shared": "workspace:*"`) | Деплой из корня workspace с `layero.json` там: `"framework": "generic"` + `buildCommand`, который сначала собирает соседа, + `outputDirectory: "apps/web/dist"` — пример ниже. `--root apps/web` загрузил бы приложение без соседа |
| `package.json` со скриптом `build`, но без известного фреймворка, html только в исходной папке | `layero.json`: `"framework": "generic"`, `buildCommand`, `outputDirectory`. Без `generic` папка считается готовой статикой, и сборка не запускается |
| Сервер без известного фреймворка (`http.createServer`, скрипт `start`) | `-t node_web` / `-t python_web` или `layero.json`: `runtime` + `startCommand` |
| `frontend/` и `backend/` рядом | `layero.json` с обоими блоками — «Раскладка fullstack»; `next_action` уже содержит файл |
| Папка результата задана флагом в скрипте сборки (`vite build --outDir public_html`) | `layero.json`: только `outputDirectory`. Детект читает файлы конфига, не флаги скрипта; без ключа платформа смотрит в папку фреймворка по умолчанию и может отдать исходный `index.html` вместо сборки. CLI называет флаг в `hint` |

**Чеклист сервера — `--dry-run` код не читает.** Узнанный сервер
(`confident: true`) всё равно может упасть на `launch`, и текст ошибки
(«Приложение не успело запуститься за 30с», `container failed to start in
time`) причину не называет. До первого деплоя открой файл входа:

1. Он слушает `0.0.0.0`, не `127.0.0.1` / `localhost`
   (`app.listen(port, "0.0.0.0")`, `uvicorn --host 0.0.0.0`). Это правка
   кода; ключ `layero.json` это не чинит.
2. Он читает порт из `$PORT` (`process.env.PORT`), либо `port` в
   `layero.json` называет порт, который он реально использует.
3. Команда запуска выполняет файл, который существует **после** сборки:
   TypeScript-сервер стартует как `node dist/index.js`, никогда как
   `node server/index.ts`. Если скрипт `start` в `package.json` неверный,
   задай `startCommand`.

Проект, созданный CLI старше 0.11 — или импортированный из репозитория
через `projects create --repo` до CLI 0.11.4 или через MCP `import_repo` до
2.3.1 — может нести догадку того инструмента в настройках; лог сборки
показывает её как `(from hint)` / `(from dashboard)`, а `--dry-run` — с
`sources` = `project settings`. `layero.json` всегда побеждает.

## Что детект уже делает — не трогай

- **Фреймворк** обычного одного приложения (Vite, Astro, Next, SvelteKit,
  Nuxt, CRA, Angular, Docusaurus, VitePress…). Ставь `framework` только
  когда детект ошибся: Storybook рядом с Vite, «Static (no build)» у
  проекта, которому нужна сборка, «Other».
- **Менеджер пакетов и команду установки** по lockfile (bun → pnpm → yarn →
  npm), версию менеджера из `packageManager`.
- **Команду сборки**: скрипт `build`. Не пиши `npm run build` в файл — это
  уже значение по умолчанию, и запись закрепляет поле.
- **Папку результата** из конфига репозитория (`outDir` в vite.config,
  `outputPath` в angular.json) или из умолчания фреймворка (vite/astro
  `dist`, экспорт next `out`, CRA `build`, nuxt `.output/public`, sveltekit
  `build`).
- **Версию Node**: `.nvmrc` → `.node-version` → `engines.node` → умолчание.
- **Режим Next.js** (сервер или экспорт): из `next.config` и результата
  сборки.
- **Команду запуска и порт** runtime-приложения, по типу.
- Флаги установки платформы (`--ignore-scripts`, `--no-audit`…)
  дописываются к **любой** команде установки и отключить их нельзя.
  Нативные сборки postinstall нуждаются в `pnpm.onlyBuiltDependencies` в
  `package.json`, не в файле.

`{}` — допустимый файл и значит «определи всё». `$schema` на сборку не
влияет.

## Ключи — полный список

Существуют только эти имена. **Неизвестный ключ сборку не роняет: он молча
пропускается с предупреждением**, и будет казаться, что ты что-то настроил.
В бою встречались и каждый раз игнорировались: `static`, `headers`, `type`,
`dir`, `build_cmd`, `output_dir`, `start_cmd`, `install_cmd`,
`rootDirectory`, `framework: "node"`. `type` пишут по аналогии с флагом
`--type`: для имени фреймворка используй `framework`, для типа контейнера
(`node_web`, `python_web`, …) — `runtime`; `deploy --dry-run` предупреждает
про `type` в `layero_warnings` ещё до загрузки.

| Ключ (короткий псевдоним) | К чему относится | Смысл |
|---|---|---|
| `framework` | сборка | Имя фреймворка; побеждает детект. |
| `installCommand` (`install`) | сборка | Установка зависимостей. Для приложения в контейнере применяется **только к Python** (заменяет шаг `pip install -r requirements.txt`); **сервер Node (`node_web`, `ssr_next`) его никогда не выполняет** — установка выбирается по lockfile. |
| `buildCommand` (`build`) | сборка | Команда сборки целиком. |
| `outputDirectory` (`output`) | только статика | Папка с `index.html` после сборки, относительно корня приложения. **Для контейнерного приложения принимается, но никогда не применяется**, и предупреждения нет. |
| `nodeVersion` (`node`) | сборка | Мажорная версия Node, например `"22"`. Перекрывает `.nvmrc` / `engines`. |
| `runtime` | тип | `ssr_next`, `node_web`, `python_web`, `streamlit`, `gradio` (больше ничего; `streamlit` / `gradio` требуют `app.py`): запускать приложение в контейнере, а не как статику. На верхнем уровне побеждает тип проекта. |
| `startCommand` (`start`) | только runtime | Команда внутри контейнера, относительно `/app`. Без runtime ничего не делает. |
| `port` | только runtime | Порт, который слушает приложение. Платформа задаёт контейнеру `$PORT`; приложению, которое слушает `$PORT`, ключ `port` не нужен. Пиши его только когда приложение игнорирует `$PORT`. |
| `memory_mb`, `cpu_quota`, `idle_timeout_s`, `preload` | только runtime | Ресурсы контейнера и таймаут сна. |
| `env` | только runtime | **Несекретные** переменные контейнерного приложения (сборка и запуск); имя, заданное здесь, перекрывает переменную проекта с тем же именем. Статическая сборка это не читает. Файл коммитится в git. |
| `layout` | форма | `"fullstack"` явно объявляет две половины, когда детект их не увидел. |
| `frontend` { `root`, `framework`, `install`, `build`, `output`, `node` } | fullstack | Половина, которая отдаётся статическими файлами. |
| `backend` { `root`, `framework`, `runtime`, `install`, `start`, `node`, `port`, `memory_mb`, `cpu_quota`, `idle_timeout_s`, `preload`, `env` } | fullstack | Половина, которая работает в контейнере. |
| `apiPrefix` (`api_prefix`) | fullstack | Префикс пути, который уходит на бэкенд, например `"/api"`. |

Если присутствуют оба имени одного поля (`build` и `buildCommand`),
побеждает camelCase, второе сообщается как предупреждение. `$schema` и
`ignore` (зарезервирован, ничего не делает) тоже принимаются без
предупреждения.

Схема для редакторов: `"$schema": "https://layero.ru/schema/layero-v2.json"`.

## Минимальные примеры — одна боль, одно поле

Неверная папка результата, больше ничего:

```json
{ "outputDirectory": "dist/client" }
```

Определён как «Static (no build)», а это приложение Vite:

```json
{ "framework": "vite", "outputDirectory": "dist" }
```

Сервер Node, который детект принял за статический сайт:

```json
{ "runtime": "node_web", "startCommand": "node dist/server.js", "port": 3000 }
```

Сервер на TypeScript: сборка контейнера ставит `devDependencies` и
запускает скрипт `build`, поэтому `startCommand` указывай на
**скомпилированный** файл, никогда на исходник `.ts`. Одного
`startCommand` достаточно, когда лог уже говорит, что проект —
runtime-приложение; добавляй `runtime`, когда его опубликовали как
статические файлы.

```json
{ "runtime": "node_web", "startCommand": "node dist/index.js" }
```

Приложение workspace, которое импортирует соседний пакет (файл в корне
workspace, деплой из корня workspace):

```json
{
  "framework": "generic",
  "buildCommand": "pnpm --filter @scope/shared build && pnpm --filter @scope/web build",
  "outputDirectory": "apps/web/dist"
}
```

Приложение FastAPI с нестандартной точкой входа:

```json
{ "runtime": "python_web", "startCommand": "uvicorn app.main:app --host 0.0.0.0 --port $PORT" }
```

Только версия Node (и только если в репозитории нет `.nvmrc` /
`engines.node`):

```json
{ "nodeVersion": "22" }
```

### Раскладка fullstack

Фронтенд и бэкенд в одном репозитории, API под `/api`:

```json
{
  "frontend": { "root": "frontend", "output": "dist" },
  "backend": { "root": "backend", "framework": "fastapi" },
  "apiPrefix": "/api"
}
```

- **Внутри половин используй короткие имена ключей** (`root`, `framework`,
  `install`, `build`, `output`, `node`, `start`, `port`). Длинные имена
  верхнего уровня (`buildCommand`, `outputDirectory`, `startCommand`) там не
  контракт.
- Бэкенду обычно нужны только `root` и `framework`: для FastAPI, Flask,
  Django, Express команда запуска и порт выводятся. Добавляй `start` /
  `port` только когда запуск падает.
- Нужны оба блока: один блок сам раскладку не включает, с `"layout":
  "fullstack"` или без него.
- `root` должен быть существующей папкой. Половина в корне репозитория
  получает пустой `root` (`"root": ""` или без `root` вовсе). Ошибка
  перечисляет настоящие папки — копируй из неё.
- Называй бэкенд через `framework` (`fastapi`, `express`, `django`…).
  `backend.runtime` тип контейнера **не** выбирает — это делает настройка
  проекта, а несовпадение только сообщается в логе.
- **Блоки `frontend` + `backend` целиком заменяют настройки fullstack из
  панели.** Блоки с выдуманными ключами (`dir`, `build_cmd`, `start_cmd`)
  выключают эти настройки и ничего не возвращают: проект, который собирался,
  перестаёт собираться. Если проект уже собирается из настроек панели, блоки
  не добавляй.

## Ошибки внутри файла, которые тихо ломают сборку

1. **Невалидный JSON** (висячая запятая, комментарии) отключает файл
   **целиком**: сборка идёт, как будто файла нет. Статическая сборка
   печатает предупреждение; контейнерная — ничего. Один проект так выпустил
   шесть сборок подряд. Проверяй до коммита.
2. **Анкета вместо исправления**: все поля заполнены умолчаниями (`npm ci`,
   `npm run build`, `dist`). Это самый частый файл в бою и самый
   бесполезный; `npm ci` без lockfile — готовый сбой.
3. **Закреплённое неверное значение**: `"output": "."` у проекта, который
   собирается, `"output": ".next"`, `"install": "true"` (выполняется
   буквально — ничего не устанавливается), `"build": ""`. Платформа
   выполняет написанное и не подставляет лучшую догадку.
4. **`outputDirectory` у контейнерного приложения** и **`startCommand` /
   `port` без `runtime`**: принимаются, сохраняются, никогда не
   используются, предупреждения нет.
5. **`runtime`, который противоречит типу проекта**: побеждает ключ
   верхнего уровня. Если это было не намеренно, одна строка меняет, как
   отдаётся сайт. `backend.runtime` внутри блока fullstack — наоборот:
   побеждает настройка проекта, ключ игнорируется с заметкой в логе.
6. **Файл не в том месте** в монорепо: он читается из корня приложения, не
   из корня репозитория.
7. **Секреты в `env`**: файл лежит в git.

## Файл или настройки проекта?

- Бери **файл**, когда значение должно ехать вместе с кодом (каждая ветка,
  каждый клон) и владелец согласен, что поле закрепляется в панели.
- Бери **настройки проекта** (`--type`, `--root`, панель) для разового
  исправления, для всего, чему в файле нет ключа, и когда ты не владелец
  договорённостей репозитория.
- Порядок приоритета, сверху вниз: `layero.json` → настройки проекта →
  подсказка CLI (`--type`, `framework_hint` в `.layero/project.json`) →
  репозиторий (`.nvmrc`, `engines`, `packageManager`, файлы конфига) →
  умолчание фреймворка.

## Как проверить

После каждой правки найди в логе сборки (`deploy_logs` /
`npx layero@latest logs`) оба признака:

1. **Применённое значение** с пометкой источника. Статическая сборка:
   `[config] framework=vite (from layero.json)`,
   `[config] build=`…` (from layero.json)`,
   `[config] install=`…` (from layero.json)`,
   `[config] output=dist/client (from layero.json)`,
   `[config] node=22.x.y (layero.json)` — у строки Node нет «from».
   Любой другой источник значит, что твоё поле не применилось (у проекта,
   созданного CLI старше 0.11 или импортированного из репозитория CLI
   старше 0.11.4 или MCP старше 2.3.1, `(from dashboard)` и `(from hint)`
   могут быть догадкой того инструмента): `(from dashboard)`,
   `(from hint)`, `(auto-detected)`, `(from package.json scripts)`,
   `(from lockfile)`, `(from vite config file)`, `(default for vite)`,
   `(project settings)`, `(.nvmrc)`, `(engines.node)`, `(default)`.
   Контейнерная сборка: `start command: …` (печатается без источника —
   сравни текст со своим `startCommand`), `install command: … (источник: layero.json)`
   (только Python), `env: N from project, N from layero.json`.
   Fullstack: `fullstack: frontend='frontend' backend='backend' api_prefix=/api`
   и `fullstack frontend: install=… build=… output=…` — если этих двух строк
   нет, раскладка не распознана.
2. **Нет предупреждений от файла.** Любое из этих значит, что файл сделал
   не то, что ты думаешь:
   - `[config] layero.json: unknown keys ignored: …`
   - `[config] layero.json: invalid JSON at line N col N`
   - ``[config] layero.json: `build` must be a non-empty string — ignored``
   - ``[config] layero.json: `buildCommand` и `build` — одно и то же поле; применяется `buildCommand` ``
   - `[config] WARNING: unknown framework '…' (layero.json). Known: …. Auto-detected as '…'.`
   - `layero.json requests runtime '…' while the project is set to '…' — the file wins`
   - `[config] в layero.json объявлен бэкенд «…», но проект настроен как «…» — собираем по настройке проекта`
   - ``[config] layero.json: объявлен `layout: "fullstack"`, но `backend` не описан — раскладка не применится``
   - `[output] в '…' нет index.html. Платформа не подменяет заданный каталог`
   - ``[config] предупреждение: `…` слушает только localhost — контейнер будет недоступен``
   - `[config] node: layero.json перекрыл .nvmrc=…` (к сведению: теперь два источника)
   - `Фронтенд указан в каталоге …, но такого каталога в репозитории нет` (или `Бэкенд …`; это роняет сборку)

**Контейнерные приложения: `ready` ждёт адрес.** CLI (0.11+) выдаёт
`ready` только когда URL отвечает приложением, а не страницей платформы
(ждёт до 90 с). `edge_ready: false` в `ready` значит, что приложение не
поднялось — читай `npx layero@latest logs --runtime`. В чат ссылку на сайт
всё равно верни только если `edge_ready` истинно; иначе скажи, что сайт не
отвечает.

**Строки, которые на успешном деплое похожи на ошибки, но ими не являются:**
`smoke: 2 из 3` / `Бэкенд отвечает по /api/ — код 404` (проба попала в путь,
для которого у приложения нет маршрута; деплой судят по итоговому статусу,
не по этой строке), `npm warn config production Use --omit=dev` (флаг
установки платформы), «сборке фронтенда будут отобраны непубличные
переменные … режим warn» (к сведению), «статику раздаёт сам контейнер: не
нашли, что выгрузить» на половине бэкенда fullstack-проекта (фронтенд
выгружается своей стадией). Не «чини» их.

Затем подтверди результат, не сборку: `site_status` или `GET` по адресу из
события `ready`. Зелёная сборка с красным запуском — всё равно сбой. В
ответ человеку вставь ссылку на сайт.
